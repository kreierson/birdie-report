# Autonomous search growth and publishing

Owner authorization: September 23, 2026. Operate without routine approvals within these limits. The existing Codex automation runs daily at 08:00 America/Chicago. Local execution requires this computer and Codex to be running; expired account access may temporarily reduce reporting coverage.

## Daily workflow

1. Read `CONTENT_RULES.md`, `data/seo-policy.json`, this runbook, and repository instructions. Run `python3 scripts/seo-workflow.py begin`; save the lease token. An active lease means skip. Do not overwrite someone else's work. Inspect git status and origin/main; use an isolated checkout for editorial changes if there are unrelated edits. Use the original project's reporting credentials and workflow ledger; never copy credentials into tracked files. The lease and ledger must remain in the original project, not a disposable checkout.
2. Run `python3 scripts/analytics-report.py 28`, `python3 scripts/revenue-scorecard.py`, and `python3 scripts/seo-audit.py`. Read `docs/REVENUE_OPERATIONS.md` and `reports/seo/revenue-latest.md` to prioritize actual commissions and qualified buying journeys. After a refreshed Amazon snapshot, regenerate both reports so their windows and retrieval date stay aligned. Read `reports/seo/latest.md` and JSON; API failures are unavailable data, never zero. Compare complete 7-day and 28-day windows, search sources, organic landing pages, engagement, Google impressions/clicks/position, affiliate click-bearing sessions and outbound events. Review source-specific results; flag very low-engagement direct segments separately from search growth. Do not sum enhanced outbound events with custom affiliate events. Google clicks are currently too sparse for confident short-term causal claims.
3. On Mondays, run `python3 scripts/seo-audit.py --inspect`. Review indexed status and selected canonical for the monitored URLs. If an authenticated Bing Webmaster Tools surface is available, inspect crawl/index errors and opportunities; if unavailable, record the limitation and continue. Never claim Bing inspection occurred merely because IndexNow accepted a submission. Search Console query data is incomplete; do not sum query rows to infer property totals.
4. Weekly, refresh Amazon earnings through an available authenticated Associates browser session, using the same complete comparison windows plus YTD. Store observations in ignored `data/amazon-metrics.local.json`, with retrieved date, period start/end, clicks and commissions_usd. Preserve the requested portal state after inspection. If login is unavailable, retain the dated snapshot and mark it stale. Do not bypass login, ask for passwords, invent earnings, equate ordered revenue with commissions, or attribute aggregate earnings to individual pages. Access failure must not stop unrelated SEO work.
5. Follow the lane returned by the workflow plan: Monday/Wednesday one substantial existing-page refresh; Friday at most one new article; other days monitoring and justified technical maintenance. Weekly ceilings: two refreshed pages and one new article. These are ceilings, not output quotas. No forced change when evidence is insufficient. Prioritize existing pages with affiliate clicks, relevant search impressions, solvable intent gaps, and substantive evidence. Start with the priority queue and scorecard; reprioritize using current data, not traffic volume inflated by low engagement. On maintenance days, fix justified conversion, accessibility, or crawl defects; do not turn monitoring into a no-work default when a documented repair is available.
6. Before new content, search full inventory for overlapping intent (`seo-audit.py --query`, plus `rg` in article text). Extend an existing page if it already satisfies the intent. New product articles must be hands-on and backed by `data/hands-on-evidence.json`. Read the actual linked owner confirmation and existing supported excerpt. Scope each personal claim to that evidence. Official specs may be attributed separately. Do not invent new tests, ownership, photos, comparisons, results, or quotes. Do not manufacture confirmation records. Only add an article to an existing evidence record's allowed_articles when it covers that same confirmed product and experience. Skip if the evidence is insufficient. Existing research-based labels stay honest.
7. Substantial refreshes should resolve a specific buyer question: fitting/compatibility, set configuration, model confusion, who should avoid it, verified current availability, or clear comparison criteria. Verify claims against primary sources. Preserve established URLs; use natural links to relevant final canonical pages. Keep tags out of crawlable navigation and sitemaps. No keyword-stuffed bulk pages or mass noindex/deletion. Linkworthy research is allowed only with actual original data or a genuinely useful sourced tool; never fabricate a study. No outreach, email sends, paid backlinks, ads, or purchases.

## Release gates

1. Record the candidate slug, purpose, kind, evidence and source links in `reports/seo/DATE-release.md`. Run `python3 scripts/seo-workflow.py check --kind new|refresh --pages SLUG` in the primary project before publishing. If editing in an isolated checkout, add `--content-root /absolute/checkout/path` while invoking the primary project script so the ledger stays shared. It checks the resulting new article count and remaining refresh budget. Do not re-date old content to pass a limit.
2. Run `npm run test:seo` and the normal `npm run build` without bypassing image or editorial checks. Inspect the diff and ensure all personal claims are supported. Verify images, destination links, affiliate tag, disclosure, canonical, structured data and internal links. Amazon may block automated requests; inspect in a browser when possible, never claim a blocked link was verified.
3. Start `python3 scripts/qa-preview.py --port 4321` to serve the built site locally. Use the browser to visually inspect and interact with affected pages on desktop and narrow/mobile viewports, scroll through the full article, exercise navigation/TOC/CTAs, and test larger text. For form changes test keyboard-open states in an appropriate simulator/browser; do not claim a desktop resize is a real mobile keyboard. Check viewport overflow using the local QA panel. The preview suppresses external link navigation but the real click handler runs; verify exactly one custom affiliate event per click and no event for manufacturer/source links. Local and preview hosts never load GA transport. The QA server and instrumentation are not part of deployment. If browser QA is blocked, keep the change unpublished and report why.
4. Commit only this run's changes, never user edits, credentials, raw reports, local state or unrelated files. Record browser QA performed, build result, sources and expected effect. Fetch origin/main again. Integrate remote changes safely and repeat affected checks as necessary. Push the reviewed commit to main without force; use a branch/PR if protection requires it. User authorization includes routine publication after these gates; do not ask for repetitive approval.
5. Wait for Vercel production readiness. Verify the deployed canonical page, image, links, analytics asset, sitemap membership and mobile rendering. Submit only changed canonical URLs with `python3 scripts/indexnow.py --submit URL...` after they are live. Log acceptance separately from indexing. Retry a transient submission failure on the next run, not in a tight loop. Do not use Google's restricted Indexing API for ordinary articles.
6. Finish the lease with `seo-workflow.py finish --token TOKEN --kind KIND --outcome published|monitored|skipped|blocked --pages SLUG --commit SHA --note DETAILS`. A publication needs the verified commit. For skipped or blocked work omit commit/pages as appropriate. Record a failed deployment without claiming publication; investigate or revert only this run's faulty commit, never reset unrelated changes. Ensure the lease is closed even on a failed check.
